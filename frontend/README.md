# SecureBank eKYC: frontend (Phases 8-12)

React 19 + Vite + TypeScript (strict) + MUI. Two portals in one app, chosen by the role in the login token:

- **Customer** (`/customer`): a four-step verification wizard (details, ID document, webcam selfie, review), a live
  status page, and *My applications*.
- **Officer** (`/officer`): the case queue (highest risk first) and the case page. The case page shows:
  - the ID image with a forgery heatmap next to the selfie;
  - the check cards and the extracted fields compared with what the applicant typed;
  - the decision and its evidence, the official summary and the audit trail;
  - Approve / Reject buttons, each with a mandatory reason;
  - and **Analytics** (`/officer/analytics`): the three dashboards over the batch snapshot (below).

SecureBank is a fictional brand; the logo is a generic shield icon.

The same app also builds as a **static demo site** (Phase 11, *demo mode*) for GitHub Pages: see
[Demo mode](#demo-mode-static-site-phase-11) below. There the dashboards are also public, at `#/dashboards`.

## Run

The whole system starts with `scripts/run_all.sh`; see `services/README.md`. On its own:

```bash
npm install
npm run dev            # http://localhost:5173 (the API must run on http://127.0.0.1:8000)
```

- **API address:** the first of these that is set wins:
  1. `window.EKYC_CONFIG.apiUrl` from `/config.js`, written by the Docker image at container start from
     `EKYC_API_URL`;
  2. `VITE_API_URL` at build time (see `.env.example`; copy it to `.env.local` to change it);
  3. `http://127.0.0.1:8000`.
- **CORS:** the API allows the origins `http://localhost:5173` (dev server) and, in Docker,
  `http://localhost:3000`. Open the app as `localhost`.

**Docker (Phase 9):** `docker compose --profile app up -d --build` (from the repository root) serves the built
app at http://localhost:3000.
- `Dockerfile`: stage 1 runs `npm ci` and `npm run build` with Node 22; stage 2 serves `dist/` with
  `nginx-unprivileged` (non-root, port 8080 inside; config in `docker/nginx.conf`).
- Unknown paths fall back to `index.html` (client-side routes). Hashed assets are cached for a year, and
  `config.js` is never cached.
- `docker/40-ekyc-config.sh` writes `config.js` at container start. One image works for any API address.

| Script | What it does |
|---|---|
| `npm run dev` / `build` / `preview` | Vite dev server / production build into `dist/` / serve the build |
| `npm run lint` | ESLint: TypeScript, React hooks (incl. React Compiler rules), jsx-a11y accessibility rules |
| `npm run typecheck` | `tsc -b` in strict mode |
| `npm test` | Vitest (jsdom): route guards, API client errors, customer status mapping, heatmap, queue, upload checks |
| `npm run e2e` | Playwright, Chromium (headless shell only): the full flow against the running system |
| `npm run dev:demo` / `build:demo` / `preview:demo` | The same three in demo mode (`--mode demo`, `.env.demo`): the static demo site, built into `dist-demo/` under `/eKYC-Verification/` |
| `npm run e2e:demo` | Playwright against the demo build (builds it first, serves it like GitHub Pages; no backend). Screenshots in `reports/phase11/screenshots/` |
| `npm run record` | The same flow in a visible, slowed-down browser with video on: backup footage for the demo video (`playwright.record.config.ts`; videos in `reports/phase10/video/`; needs `npx playwright install chromium`, ~380 MB) |
| `npm run gen:api` | Regenerate `src/api/schema.d.ts` from the API's OpenAPI schema (`openapi.json`, written by `scripts/export_openapi.py`; no server needed) |

The e2e test needs the following, and saves screenshots to `reports/phase8/screenshots/`:
- `scripts/run_all.sh` running;
- `scripts/make_demo_samples.py` run once;
- the browser: `npx playwright install --only-shell chromium` (~102 MB).

## Structure

```
src/
  api/client.ts          the ONLY module that calls the API (typed with the generated schema.d.ts); ApiError;
                         a 401 logs the user out
  auth/                  session (memory + sessionStorage), AuthProvider (login, logout, expiry timer),
                         RequireRole (route guard)
  customer/              customerStatus.ts (the customer-safe mapping), wizard steps, webcam, status page (SSE)
  officer/               queue, case page, heatmap (heatmap.ts = geometry), check cards, decision dialog
  components/ pages/     app shell (top bar, skip link), login, not found
  demo/                  demo mode only: client.ts (fixture-backed EkycApi), data.ts (lazy chunk), fixtures/
                         (generated by scripts/export_demo_fixtures.py + web images), banner, landing page, customer/
  dashboards/            the analytics dashboards (Phase 12, a lazy chunk): snapshot.json (generated) + snapshot.ts
                         (typed parse), transforms.ts (every number), palette.ts, one file per dashboard tab
e2e/kyc-flow.spec.ts     Playwright end-to-end flow (the real system)
e2e-demo/                Playwright tests of the static demo site (demo-site.spec.ts, dashboards.spec.ts)
```

## Design decisions

- **Login token storage.** The JWT is kept in memory and mirrored to `sessionStorage`, so a reload keeps the user
  logged in within the tab, and closing the tab ends the session. **In production an httpOnly, Secure, SameSite
  cookie set by the API is the better choice.** JavaScript (and so an XSS bug) cannot read such a cookie. Here it
  would need cookie handling plus CSRF protection in the API, which is out of scope for the demo.
- **Auto-logout.** It happens on any 401 from the API, and also by a timer when the token expires (30 min).
- **Statuses (Phase 9 lifecycle).**
  - Only `DECIDED` waits for an officer (manual review). It is the officer queue's default filter, labelled
    *Awaiting officer*.
  - An auto-approval arrives as `APPROVED` (labelled *Auto-approved*; *Approved by officer* after a review).
  - A retake request arrives as `RESUBMIT_REQUESTED`.
  - The customer stream ends at any of these statuses; only `DECIDED` is polled afterwards, for the officer's
    decision.
- **Customers never see fraud signals.**
  - Every customer screen receives only a `CustomerStatus`. `toCustomerStatus()` builds it by copying a fixed
    whitelist of fields.
  - The API itself sends no scores to customers.
  - Three tests prove it:
    - the mapping is a whitelist;
    - a status page rendered with leaked fields shows none of them;
    - a scan finds no fraud-signal names in any customer source file.
  - The *what to retake* text is shown only for RESUBMIT_REQUESTED.
- **Live status uses Server-Sent Events** (`EventSource` with `?token=`, because browsers cannot add headers to it).
  - The stream is closed at a final status; otherwise EventSource would reconnect.
  - If the stream fails (network, expired token), the page polls instead.
  - A case under review is re-checked every 15 s for the officer's decision.
- **The selfie step is camera first**, using `getUserMedia`. The preview is mirrored like a mirror; the saved
  photo is not. If the camera is denied or missing, the page explains why and offers an upload instead. Upload is
  also always available.
- **Forgery heatmap.**
  - The model scores overlapping 224 px tiles (stride 112) on the page resized to 1280 px.
  - The page is cut along every tile edge, and each cell gets the highest score of the tiles covering it. Drawing
    the tiles themselves would stack transparent squares.
  - Colour: a single-hue sequential blue ramp, with near-zero cells left out so the document stays readable.
  - The highest-scoring tile is outlined, and the legend marks the review (0.729) and suspected (0.857)
    thresholds.
- **Accessibility.**
  - Every input has a label; status chips pair an icon with text, so colour is never the only signal.
  - The status palette is used only for borders and icons; text stays in ink colours, which keeps contrast at
    WCAG AA.
  - The step heading takes focus on each wizard step; there is a skip link; progress is announced in a live
    region; dialogs focus their first field.
- **Code splitting.** Each portal's pages load on demand.
- **Tool versions.**
  - TypeScript is pinned to 5.9 because typescript-eslint and openapi-typescript do not support TypeScript 7 yet
    (create-vite now defaults to TS 7 and oxlint).
  - `eslint-plugin-jsx-a11y` declares ESLint ≤ 9, so `package.json` has an `overrides` entry. It runs correctly on
    ESLint 10.

## Demo mode: static site (Phase 11)

`VITE_DEMO_MODE=true` (set by `--mode demo` through `.env.demo`) builds the app for GitHub Pages, with no backend.
- **Same pages, another client.** `api` in `src/api/client.ts` is either the HTTP client or `demoApi`
  (`src/demo/client.ts`): two implementations of one `EkycApi` interface. The pages do not know which one they use.
  The only demo-specific UI is the banner, the landing page with one-click logins, the sample picker that replaces
  the upload area and the camera, the replay note on the status page and the "this tab only" note in the decision
  dialog.
- **Nothing computed or invented.**
  - The fixtures are what the real API returned for real runs (`scripts/export_demo_fixtures.py`):
    - the customer status events, recorded live over SSE with their timing;
    - the officer queue rows and case details.
  - The demo client replays them and never calls the network (Vitest stubs `fetch`, `EventSource`,
    `XMLHttpRequest` and `WebSocket` to prove it).
  - A submission is accepted only if both images are bundled samples (recognised by SHA-256) with the details the real
    run used.
- **Replay timing.** The recorded events keep their real relative times, sped up so that a case finishes in about
  10 s (a 0.6 s run stays 0.6 s).
- **Officer decisions** live in memory: this browser tab only, gone on reload, labelled in the dialog and in the
  audit trail.
- **Relative times** (the queue's Waiting column) are measured at the time of recording (the fixtures'
  `generated_at`), not today's date, and labelled "at time of recording".
- **Routing and paths.**
  - Hash URLs (`#/officer`): GitHub Pages serves only files, so a reload or a shared link never asks the server for a
    path it does not have.
  - `base` is `/eKYC-Verification/` (override: `VITE_DEMO_BASE`).
- **A normal build is unchanged.**
  - `__DEMO_MODE__` is a build-time constant, so every demo branch and module is removed from it.
  - A small Vite plugin stops it from even loading `src/demo/data.ts`; otherwise Vite would copy the demo images into
    `dist/`.
  - Checked: the same file list and size as before Phase 11.
- **Links.** `src/demo/config.ts` holds them. The video link is an empty placeholder, shown as "Coming soon". Set it
  with `VITE_DEMO_VIDEO_URL`, or as the repository variable `DEMO_VIDEO_URL` for the Pages workflow. The landing page's
  **Dashboards** link opens this site's own `#/dashboards` (Phase 12).

## Analytics dashboards (Phase 12)

Three tabs (Operations, Risk & fraud, Model performance) over the Phase 9 batch. They are in the officer portal
(`/officer/analytics`) and, on the demo site only, public at `#/dashboards`. Both use the same bundled snapshot and
say so on every dashboard: *Synthetic data*, *Batch snapshot*, *Data as of …* (UTC).

- **Data:** `src/dashboards/snapshot.json`, generated from `dashboard/data/tableau/*.csv`:

  ```bash
  npm run gen:dashboards    # = ../.venv/bin/python ../scripts/export_dashboard_snapshot.py
  ```

  - The format is compact: the column names once, then one array per row. Empty cells are `null`.
  - The same PII guard as the CSV export runs, plus a check that no value looks like an e-mail or a real id.
  - `snapshot.ts` checks every column and value type when it loads.
  - A pytest test fails if the file is out of date with the CSVs.
- **Numbers:** `transforms.ts`, a set of pure functions.
  - Sums of `applications`, and averages of the 0/1 columns (empty = does not apply).
  - Medians and the 95th percentile use the numpy/pandas interpolation.
  - **No double counting:** `risk_fraud` has a row per reason, so every case-level number uses `caseRows()`, each
    case's first row.
- **Charts:** MUI X Charts (`@mui/x-charts`, the MUI team's library for MUI 9). Its legends, tooltips and keyboard
  navigation are built in.
  - Decision reasons are a plain bar list instead: they are long sentences, which a chart axis would cut short.
  - The system-vs-truth matrix is an MUI table with tinted cells, each labelled with its verdict.
- **Colours** (`palette.ts`): the app's status colours and the data-viz reference series colours.
  - Every set was checked for colour-blind separation.
  - The system outcome "Resubmit required" is neutral grey, because orange beside amber failed the check.
- **Accessibility:**
  - a legend or labels on every chart, and a **Table** button showing the same numbers;
  - tick labels shortened on phones;
  - no sideways scrolling at 390 px.
- **Filters** (document type, outcome) sit in one row above the charts and apply to every chart of the two batch
  dashboards. The model metrics are offline evaluations, so the filters do not apply there.
- **Tests:**
  - `transforms.test.ts`: the counting rules, statistics and orderings;
  - `selfCheck.test.ts`: the snapshot against `reports/phase9/batch_summary.json` (150 applications, 32.7 / 62.7 /
    4.7 %, 67 of 68 caught, 27 false alarms, the funnel, the confusion table);
  - `e2e-demo/dashboards.spec.ts`: all three tabs on the built demo site, filters, table view, phone width, the
    officer's Analytics tab. Its screenshots go to `reports/phase12/`.
- **Size:** a separate chunk of 132 KB gzipped (library + data + code), loaded only when a dashboard opens. The other
  pages load as before.
